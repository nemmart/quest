## 0. The number

**758 of 758 game call sites resolve to a static target — 100%.** There is
no register-indirect `LCALL`/`XCALL`/`LJSR` anywhere in the game range
(`--check`, hazard 8 is a runtime-only phenomenon). The unresolved remainder
is therefore not a set of edges but **one node with no inbound edge of any
class: TERRAIN_HELP** (§6).

Cross-check: `Disassembled/quest.callsites`, produced by a different tool
from the disassembly, counts 754 game-target sites. The difference of 4 is
exactly the sites whose target is not an addrbook entry — SQR31?3 ×3
(7016872A, 701687D5, 7017CF74) and INIT_SHARED_DATA ×1 (7015C00B) — which
that census excluded and this one keeps as nodes. `--check` asserts the
equality.

### 5.3 Signal, non-local goto and task-spawn edges — 26 + 26 + 1

Kept as separate classes (hazard 5; DESIGN §11). Facts a future session
should not rediscover the hard way:

- **Every O.ON establisher and its handler are in the same family.** The
  handler is always the `nocall` entry immediately following the
  `WBR` that skips over it (`XLEF 2,[pc+5]`). ON-units nest as handler
  chains: ALLY_PLAYER → .1 → .2, KILL_PLAYER → .1 → .2 → .3, LOGON → .1 →
  .2, OP_EDIT has three (.1→.2→.3 from the parent, .5 from .4, .7 from .6,
  .9 from .8). These are handlers established *inside* handlers, not two
  levels of procedure nesting — the addrbook's `nested` flag on a `#` line
  is this (Salvage F3/F10).
- **Every I.GOTO lands in its own family.** 23 land inside the same
  piece's range (the handler jumping to its own epilogue label). **Three
  land in a *sibling* piece's range**: DROP.1's at 701696C3 → 70169659 in
  DROP's range; ATTACK.4's at 7015F730 → 7015F70F in ATTACK.3's range;
  KILL_PLAYER.1's and KILL_PLAYER.4's → 7016E5AD in KILL_PLAYER.2's range.
  **These are F10 interleaving, not nesting**: the label is parent-body code
  whose address happens to fall in an ON-unit's addrbook range because the
  unit was emitted in the middle of the parent. A non-local goto from a
  handler to its establisher's label is the expected PL/I shape

## 7. What this graph says about DESIGN §9.4

- **Tractable.** 80 nodes, 9 strata, no cycles, 20 translatable leaves, and
  the leaves are called from 1–27 families each: the frontier grows
  monotonically and the replaced set stays downward-closed. With the 12
  routines proposed in Order.md replaced, `--frontier` opens 22 further
  candidates.
- **But the graph is wide, not deep.** 37 of START_TURN's callees are
  siblings at h≤4; the program is a dispatcher over ~35 commands, most of
  which are 500–4,000-statement subtrees. Bottom-up gives an order *within*
  each subtree; it does not say which subtree to enter, and that choice is
  where coverage (Coverage.md) matters more than depth. See REPORT §own read.

## Note added at integration (a002): DIED is not only the death routine

`DIED` is **"(re)initialise a character and place them in the world"**. It is
reached from death AND from **first character creation**: START_TURN block
70178246 prints *"What would you like your character to be — 'W' = wizard,
'C' = cleric, 'D' = druid, 'F' = fighter 'B' = barbarian"* (literal
0x7017816B) and calls DIED at 7017868D / 70178801. DIED then reaches
REPOSITION (70166323) → PICK_X_Y (70176FC7) and PLACE_PLAYER (70176FD1).
*"Better luck next time!"* is the death branch only.

The name misleads; read the node as *respawn/initialise*. Consequence for
coverage: **creating a character with unused initials reaches PICK_X_Y,
REPOSITION, PLACE_PLAYER, DIED and part of START_TURN with no data fixture
at all** — see `docs/Project47/a002-character-creation-reaches-pick-x-y.md`.
